# v4 Candidate Generation Bridge

The evaluation system must compare actual prompt strategies, not merely the same raw task text on different target models.

## Three strategy paths

- `neutral` is materialized deterministically by the repository.
- `legacy` must be materialized by an external host that executes the frozen legacy prompt-generation route.
- `v4` must be materialized by an external host that executes the v4 Prompt Contract/Core/Task/Model-Delta route.

The repository intentionally does not emulate legacy or v4 with hand-written templates because that would invalidate the comparison.

## Materializer protocol

A materializer receives one plan job as JSON on stdin and emits exactly one JSON object on stdout.

Required output fields:

```json
{
  "strategy": "legacy",
  "prompt": "...exact generated prompt...",
  "prompt_sha256": "...",
  "generator_model": "optional exact generator model",
  "generator_runtime": "optional host/runtime",
  "materializer_revision": "required revision identifier"
}
```

The bridge recomputes the prompt SHA-256 and rejects mismatches.

## Provenance boundary

`generator_model` is not the same as the evaluation `target.model`. A prompt may be generated by one model and later executed on another target model.

`materializer_revision` should identify the exact legacy/v4 implementation or host revision used to produce the candidate. Live release evidence should additionally preserve repository revision and profile revision in the final evaluation result.

## Security

Materializers are invoked without a shell. They receive no repository credentials from this bridge. Any model/API credential handling belongs to the external host.

## CI

The repository uses `tests/v4/mock_candidate_materializer.py` only to verify protocol behavior. Synthetic candidates are not release evidence and cannot change support maturity or the release gate.
